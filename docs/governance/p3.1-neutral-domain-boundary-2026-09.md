# Mustashark — P3.1 Neutral Domain Boundary

**Effective:** 2026-09-01  
**Construction branch:** `construction/lawyer-os-v1-p1-audit-2026-09`  
**Status:** `P3.1 IN PROGRESS / BOUNDARY ESTABLISHED`

## 1. Purpose

P3.1 establishes the implementation boundary for Lawyer OS v1 before feature construction expands.

The Neutral Core is intentionally limited to:

- Identity / authentication integration
- Lawyer workspace
- Lawyer-owned client relationships
- Matters / cases as neutral work containers
- Documents and document metadata
- Scheduling / availability
- Secure messaging
- Notifications
- Audit events
- Export to the lawyer

This phase does **not** authorize or import financial, marketplace, settlement, custody, escrow, wallet, commission, payout, or client-fund behavior.

## 2. Hard dependency rule

Neutral Core modules MUST NOT require any of the following as a prerequisite for their existence or normal operation:

- agreements / legal representation contracts
- representation quotes
- payment proofs
- platform dues / commissions
- representation finance
- lawyer wallet / bank settlement
- escrow / milestone funding
- client-fund custody
- marketplace ranking / referral monetization

Legacy implementations may remain in the repository and remain available for historical evidence, but they are not Neutral Core dependencies.

## 3. Current repository findings

### Clients

A lawyer client directory already exists, but its current implementation derives the relationship from `bookings`. That is acceptable as a legacy source for discovery, but it is not the target Neutral Core ownership model. The new boundary treats **Lawyer ↔ Client relationship** as a first-class domain concern rather than a side effect of booking history.

### Matters / Cases

The current `cases` table is coupled to `agreements` through a mandatory `agreementId`, and the current case controller creates a case from an agreement. This is explicitly classified as **legacy representation coupling**.

P3.1 therefore does not silently reuse the current case creation path as the Neutral Matter API.

### Documents

Existing document/representation document implementations are similarly classified by ownership and lifecycle. Neutral document construction must not require an agreement, quote, payment, or representation state merely to store or manage a lawyer-owned document.

### Shared schema surface

The DB schema currently exports both neutral-adjacent and legacy financial/representation tables from the same package surface. This is not itself a production defect and must not trigger destructive cleanup. P3.1 instead establishes a **dependency discipline**: Neutral Core code imports only the authoritative tables/services required by its own domain boundary.

## 4. Target domain model

```text
Identity
   │
   ├── Lawyer
   │      │
   │      ├── Lawyer Workspace
   │      │
   │      ├── Lawyer ↔ Client Relationship
   │      │             │
   │      │             ├── Matter
   │      │             │     ├── Documents
   │      │             │     ├── Tasks / Workflow
   │      │             │     ├── Schedule / Meetings
   │      │             │     └── Secure Messages
   │      │             │
   │      │             └── Audit Events
   │      │
   │      └── Export
   │
   └── Client
```

The model deliberately avoids making a financial or representation object the root of the lawyer's workspace.

## 5. Ownership / authorization contract

Every Neutral Core resource must resolve authorization from server-side authenticated identity plus explicit resource ownership/relationship checks.

Minimum rules:

1. A lawyer may access only clients and matters within the lawyer's authorized scope.
2. A client may access only resources explicitly shared with that client.
3. An administrator does not receive unrestricted access to confidential matter content merely by possessing an admin role.
4. Resource IDs supplied by clients are never treated as authorization.
5. Sensitive actions use server-generated actor identity and timestamps.
6. Authorization failures must not leak resource existence or confidential data beyond the minimum required response.
7. Every sensitive read/write/share/export operation must have an auditable event where applicable.

## 6. Data minimization

Neutral Core entities must contain only data required for their operational purpose.

Financial fields, payment state, commission, settlement, wallet balances, escrow state and client-fund state are prohibited from becoming implicit fields of neutral entities merely for convenience.

## 7. Matter / Case transition

The existing agreement-derived `cases` state machine is retained as legacy evidence.

The Neutral Core target is a Matter abstraction whose lifecycle is independent of financial settlement and whose creation does not require an agreement or payment event.

A later migration may map historical cases into the Neutral Matter model only after a separate compatibility and data-integrity review.

## 8. Documents

Neutral document architecture separates:

- document identity
- owner / matter scope
- classification
- storage reference
- version metadata
- content integrity metadata
- access policy
- audit history
- export status

Legal-representation-specific document semantics remain outside the Neutral Core unless separately classified and approved.

## 9. Export → Lawyer

Export is a first-class capability.

The architecture must permit the lawyer to export their operational data without depending on:

- marketplace state
- platform settlement
- wallet state
- escrow state
- payment-provider state

Exports must preserve authorization, confidentiality, integrity metadata, and auditability.

## 10. Explicitly blocked imports

The following are **P3.1 hard blocks**:

## 11. P3.1 implementation sequence

```text
P3.1-A  Boundary types / contracts
P3.1-B  Lawyer ↔ Client ownership model
P3.1-C  Neutral Matter model
P3.1-D  Neutral Document ownership/scope
P3.1-E  Scheduling / Messaging / Notification boundaries
P3.1-F  Audit + Export contracts
P3.1-G  Permission / IDOR tests
P3.1-H  CI + diff audit
```

No schema migration is authorized merely to make P3.1 look complete. Schema changes require an evidence-backed need after the boundary contracts are established.

## 12. Exit criteria

P3.1 may be declared complete only when:

- Neutral Core dependency boundaries are explicit in code;
- no Neutral Core service imports financial/marketplace/custody/escrow authority;
- lawyer/client ownership checks are explicit;
- Matter creation no longer requires an agreement or payment prerequisite;
- document scope is explicit;
- audit/export contracts are defined;
- security/IDOR tests exist for the implemented boundary;
- typecheck and applicable CI pass;
- no production or `main` mutation occurred.

**P3.1 decision:** `CONSTRUCTION AUTHORIZED — NEUTRAL ONLY`.
