# P3.1-M — Resolver-Aware Boundary Guard Design — 2026-09

**Status:** DESIGNED / IMPLEMENTATION NOT YET AUTHORIZED  
**Branch:** `construction/lawyer-os-v1-p1-audit-2026-09`  
**Baseline:** P3.1-K boundary specification + P3.1-L evidence closure  
**Scope:** Guard design only. No executable guard, schema remediation, migration, or runtime authorization change is authorized by this artifact.

## 1. Purpose

P3.1-M defines the security guard that will eventually enforce the P3.1-K module/export boundary and prevent recurrence of the proven P3.1-J Neutral → Financial reachability defect.

The guard is intentionally designed around the real workspace/module resolution graph rather than keyword scanning.

## 2. Security Decision Rule

For every branch-pinned evaluation:

> If any Neutral-classified source can resolve a Financial/Marketplace authority module directly or transitively through any supported workspace/package/barrel/declaration/runtime-loading path, the guard MUST FAIL.

Likewise, any Financial → Neutral authorization implementation dependency, prohibited Neutral ↔ Financial cycle, unauthorized shared crossing, or unresolved security-relevant path MUST result in FAIL-CLOSED.

Unknown is never equivalent to safe.

## 3. Guard Inputs

The eventual implementation SHALL consume only branch-pinned repository state and deterministic local metadata:

- commit/ref under test;
- `pnpm-workspace.yaml` workspace boundaries;
- package manifests and `exports` maps;
- TypeScript configuration including `moduleResolution` and `customConditions`;
- source files;
- generated declaration files when present;
- supported import/re-export forms;
- supported dynamic loading forms that are statically discoverable;
- explicit domain classification manifest;
- exact shared-primitive allowlist.

The guard MUST NOT require Production DB access.

## 4. Domain Classification

The guard SHALL operate from an explicit classification manifest rather than filename heuristics alone.

Minimum classes:

```text
NEUTRAL
FINANCIAL
MARKETPLACE_AUTHORITY
SHARED_APPROVED
UNKNOWN
```

`UNKNOWN` is fail-closed whenever the unresolved module is reachable from a protected domain path.

The initial classification must include the P3.1-K surfaces, including Neutral modules such as:

- `neutralDocuments`
- `neutralMatters`
- `lawyerClients`
- `neutralAuditEvents`

and Financial/Marketplace authority modules such as:

- `platformDues`
- `representationFinance`
- `representationQuoteRequests`
- `lawyerProposals`
- `paymentProofs`
- Financial-coupled `agreements` and downstream representation-finance paths.

## 5. Resolution Algorithm

The authoritative graph SHALL be constructed using resolver-aware analysis.

For each source module:

1. Parse static imports.
2. Parse `export ... from` re-exports.
3. Parse `export * from` and namespace/barrel expansion.
4. Resolve relative paths using repository filesystem semantics.
5. Resolve workspace package imports through package manifests.
6. Apply package `exports` conditions exactly as configured for the tested environment.
7. Apply TypeScript `moduleResolution: bundler` and configured custom conditions where relevant.
8. Resolve extension/index/barrel behavior used by the compiler/toolchain.
9. Resolve generated declaration references where declarations participate in public package resolution.
10. Record every source → resolved module edge with the resolver path.
11. Follow the graph transitively until closure.

The implementation MUST retain both the logical module identity and the concrete resolution path so a failure is auditable.

## 6. Package Export Guard

Every protected workspace package SHALL have its public exports enumerated.

The guard MUST fail if:

- a Neutral-reachable package exports a Financial/Marketplace authority module;
- a domain barrel re-exports another domain's authority module;
- an unclassified module is exposed through a protected domain surface;
- a new export expands the Neutral reachable closure without explicit classification;
- a convenience root barrel reconstructs a prohibited combined surface.

The current `@workspace/db/schema → src/schema/index.ts` combined surface is therefore expected to fail until remediation creates compliant public surfaces.

## 7. Reverse Dependency Guard

For every Financial/Marketplace authority module, compute reverse reachability into Neutral authorization/core modules.

Forbidden examples:

```text
Financial schema/service
  → Neutral authorization implementation

Financial package entrypoint
  → Neutral authorization implementation

Financial barrel
  → Neutral authorization implementation
```

An allowed dependency may cross only through a module explicitly classified `SHARED_APPROVED` and must not transitively expose Neutral authority implementation.

The reverse graph SHALL be computed from the same resolver-aware graph as the forward graph; a separate heuristic scanner is not authoritative.

## 8. Cycle Guard

The guard SHALL detect strongly connected components across the relevant package/module graph.

FAIL-CLOSED conditions include:

- any Neutral ↔ Financial cycle;
- any Neutral ↔ Marketplace-authority cycle;
- any cycle created by re-export/barrel expansion;
- any package-level cycle that causes a protected domain to acquire another domain's authority surface.

A cycle is not considered harmless merely because runtime initialization currently succeeds.

## 9. Runtime Escape Guard

The guard SHALL inspect statically discoverable runtime-loading mechanisms, including:

- `import()` with statically resolvable specifiers;
- `require()` with statically resolvable specifiers;
- `createRequire()`-derived loading with statically resolvable targets;
- loader/bootstrap registries that enumerate modules;
- package entrypoints used by runtime registration;
- generated runtime artifacts when they are repository-controlled and form part of the executable package surface.

Rules:

1. A statically resolvable runtime load from Neutral to Financial is a hard failure.
2. A runtime target that cannot be resolved deterministically is `UNKNOWN → FAIL-CLOSED` when it originates from a protected domain.
3. Runtime registration must not be treated as safe merely because the module is not imported lexically by the caller.
4. Dynamic user-controlled module resolution is outside the proof envelope unless a separate explicit sandbox/allowlist proves it safe; absent such proof it is fail-closed.

## 10. Declaration / Build Escape Guard

Because package consumers may resolve declarations rather than source text directly, the guard SHALL inspect:

- `package.json` export targets;
- TypeScript declaration entrypoints;
- generated `.d.ts` files when committed/generated as part of the build surface;
- declaration re-exports;
- build output manifests when available.

A prohibited Financial symbol hidden behind a declaration barrel remains prohibited.

A declaration path that cannot be resolved remains `UNKNOWN → FAIL-CLOSED` for protected surfaces.

## 11. Shared Primitive Allowlist

Shared crossings are allowed only when both conditions hold:

```text
source → SHARED_APPROVED
```

and

```text
SHARED_APPROVED ↛ Financial/Marketplace authority
SHARED_APPROVED ↛ Neutral authorization implementation
```

The allowlist SHALL contain exact module identities, not broad directory prefixes or keyword patterns.

Identity/user primitives may be approved only after explicit architectural classification.

## 12. Failure Semantics

The guard SHALL produce one of three evidence states per evaluated path:

```text
PROVEN SAFE
PROVEN VIOLATION
UNKNOWN → FAIL-CLOSED
```

Aggregate decision:

```text
Any PROVEN VIOLATION  → FAIL
Any UNKNOWN            → FAIL
All relevant paths SAFE → PASS
```

There is no warning-only mode for a protected boundary.

## 13. Required Failure Evidence

Every failure SHALL report enough information to reproduce the edge:

```text
commit/ref
source module
source domain
import/export/runtime form
package entrypoint (if any)
resolver condition
barrel/re-export chain
resolved target module
target domain
classification decision
```

Example expected diagnostic:

```text
FAIL: NEUTRAL → FINANCIAL
source: artifacts/api-server/src/services/neutralDocumentAuthorization.ts
import: @workspace/db/schema
export: lib/db/package.json#./schema
barrel: lib/db/src/schema/index.ts
reachable target: lib/db/src/schema/representationFinance.ts
reason: prohibited transitive authority reachability
```

## 14. Completeness Boundary

The guard may claim repository-wide proof only when all relevant repository-controlled resolution mechanisms have been evaluated at the pinned ref.

It MUST NOT claim completeness from:

- a two-file keyword scan;
- direct-import search alone;
- schema-only inspection;
- successful TypeScript compilation;
- successful runtime startup;
- absence of observed failures in a sampled subset.

If tooling cannot resolve a relevant mechanism, that mechanism becomes `UNKNOWN → FAIL-CLOSED`.

## 15. CI Contract

The eventual CI implementation SHALL run before any merge that changes protected package/module surfaces.

Minimum sequence:

```text
Pin commit/ref
  ↓
Load explicit domain classification
  ↓
Resolve package/workspace exports
  ↓
Build complete resolver-aware graph
  ↓
Expand barrels/re-exports
  ↓
Resolve declarations
  ↓
Resolve statically discoverable runtime loads
  ↓
Compute forward + reverse reachability
  ↓
Compute cycles
  ↓
Apply shared allowlist
  ↓
Classify every relevant path
  ↓
UNKNOWN/VIOLATION → FAIL
  ↓
All relevant paths PROVEN SAFE → PASS
```

The gate must be independent of Production DB availability.

## 16. Regression Requirement

The first implementation test set SHALL include the currently proven defect as a negative fixture.

Expected result:

```text
Neutral service
 → @workspace/db/schema
 → schema/index.ts
 → representationFinance

= FAIL
```

A compliant domain-separated export surface SHALL be a positive fixture.

A hidden re-export, declaration-only leak, reverse dependency, cycle, or static dynamic-import target SHALL each have a dedicated negative fixture.

## 17. Non-Goals

P3.1-M does not authorize:

- schema/package splitting;
- changing package exports;
- changing application imports;
- authorization behavior changes;
- financial logic changes;
- marketplace execution;
- migrations;
- Production DB access;
- modification of `main`.

Those belong to a separately approved remediation phase after the guard design is accepted.

## 18. Implementation Preconditions

Before executable guard code is written, the following must remain explicit:

1. domain classification manifest is committed;
2. shared-primitive allowlist is committed;
3. resolver behavior is pinned/documented;
4. generated declaration policy is fixed;
5. runtime escape coverage is defined;
6. unknown/failure semantics are implemented as fail-closed;
7. baseline negative fixtures are identified;
8. CI execution is isolated from Production DB;
9. rollback is limited to the construction branch.
