# Mustashark — P3.1-D Neutral Document Boundary

**Effective:** 2026-09-01  
**Construction branch:** `construction/lawyer-os-v1-p1-audit-2026-09`  
**Status:** `P3.1-D IN PROGRESS / BOUNDARY BASELINED`

## 1. Decision

Neutral Lawyer OS documents are first-class operational resources. A neutral document MUST NOT require an agreement, legal-representation contract, quote, payment, settlement, wallet, escrow, marketplace state, or client-fund state merely to exist, be stored, versioned, scoped, or exported.

The existing `documents` and `legal_representation_documents` implementations are legacy surfaces and are not silently promoted into the Neutral Core.

## 2. Existing evidence

The existing `documents` table is coupled to `caseId`, while also containing owner, storage, title and status fields. This makes it unsuitable as the Neutral Matter document root without a compatibility review.

The existing `legal_representation_documents` table is explicitly coupled to `agreementId` and optionally `caseId`, and therefore remains representation-specific legacy infrastructure.

## 3. Neutral document contract

A Neutral Document has:

- stable document identity;
- lawyer ownership;
- optional Matter scope;
- title and classification metadata;
- storage reference;
- content integrity hash when available;
- lifecycle metadata;
- access policy/scope;
- auditability;
- exportability.

The document itself does not carry financial authority or representation-state authority.

## 4. Ownership and scope

Minimum authorization rules:

1. A lawyer may access a document only when the document belongs to that lawyer's authorized scope.
2. A Matter-scoped document must resolve through a Matter owned by the same lawyer.
3. A client receives document access only when the document is explicitly shared under the applicable relationship/matter policy.
4. A resource ID alone is never authorization.
5. The server resolves actor identity; client-supplied lawyer IDs are not trusted.
6. Archived/revoked Lawyer–Client relationships stop new access according to the approved relationship policy; records are retained.
7. Authorization failures must avoid unnecessary existence disclosure.

## 5. Document lifecycle

Neutral lifecycle is intentionally simple:

`draft → active → archived`

Versioning is metadata/history, not a financial or representation state machine.

Deletion is not required for normal unlink/archive behavior. Retention and legal-hold policy remain separate governance concerns.

## 6. Sharing

Sharing is an explicit authorization action. Opening an invitation, creating an account, or discovering a Matter does not itself grant document access.

A document may be shared only after the relevant authenticated relationship and scope checks pass. Sharing and revocation are auditable sensitive operations.

## 7. Storage and integrity

The application stores a storage reference rather than treating a public URL as authorization. Where content integrity is supported, the server records a content hash/version reference.

Raw storage credentials and provider-specific access controls remain outside this domain contract.

## 8. Legacy boundary

The following remain outside Neutral Core:

- `legal_representation_documents`;
- agreement-derived document workflows;
- case-handover logistics;
- payment/financial document semantics;
- representation verification semantics.

They may remain in the repository for historical/regulated workflows and must not be deleted merely to simplify the Neutral Core.

## 9. Implementation rule

**No migration is authorized by this document alone.**

Before changing the database, implementation must identify the minimum authoritative Neutral Document persistence model and verify whether the existing `documents` table can be safely extended or whether a separate table is required. The decision must preserve legacy compatibility and avoid destructive changes.

## 10. Security test targets

The implementation must eventually prove at least:

- lawyer L1 cannot read L2's document;
- lawyer L1 cannot read a document through a foreign Matter ID;
- client C1 cannot read a document outside explicitly shared scope;
- archived relationship does not permit new document access;
- tampered document/matter IDs cannot bypass ownership checks;
- admin role alone does not grant confidential document access;
- document export is scoped to the authorized lawyer;
- no blocked financial/marketplace/custody dependency is imported.

## 11. Exit criteria for P3.1-D

P3.1-D is complete only when the Neutral Document persistence/ownership contract is explicit, authorization checks are implemented, legacy representation documents remain isolated, applicable IDOR tests exist, and typecheck/CI evidence passes.

**Decision:** `CONSTRUCTION AUTHORIZED — NEUTRAL DOCUMENTS ONLY`.
