# P3.1-N — Remediation Preconditions — 2026-09

**Status:** DEFINED / REMEDIATION NOT AUTHORIZED  
**Branch:** `construction/lawyer-os-v1-p1-audit-2026-09`  
**Baseline:** P3.1-K Boundary Specification + P3.1-L Evidence Closure + P3.1-M Guard Design  
**Scope:** Preconditions only. This artifact authorizes no code implementation, schema/package remediation, migration, runtime authorization change, Financial/Marketplace execution, Production DB access, or `main` modification.

## 1. Purpose

P3.1-N defines the independent security and engineering conditions that MUST be satisfied before any future attempt to remediate the proven Neutral → Financial boundary defect by dismantling or replacing the combined `@workspace/db/schema` barrel.

The purpose is to ensure remediation is evidence-driven rather than inferred from compilation success, local behavior, naming conventions, or a partial import scan.

## 2. Governing Security Principle

No remediation step may be authorized merely because the resulting code appears cleaner or because a sampled dependency path appears safe.

The authorization condition is:

```text
REMEDIATION_ELIGIBLE
=
ALL_MANDATORY_PRECONDITIONS_PROVEN
∧
NO_UNRESOLVED_SECURITY_UNKNOWN
∧
NO_PRODUCTION_ACCESS_REQUIRED
∧
NO_FINANCIAL_EXECUTION_REQUIRED
```

If any mandatory precondition is UNKNOWN, incomplete, contradictory, or unproven, remediation remains BLOCKED.

## 3. Current Defect That Remediation Must Address

The existing P3.1-J finding is a real transitive boundary defect:

```text
NEUTRAL
  → @workspace/db/schema
  → lib/db/src/schema/index.ts
  → FINANCIAL AUTHORITY
```

The known path through `representationFinance` is a mandatory negative baseline for future validation.

Remediation MUST remove the prohibited reachable surface rather than merely hiding, renaming, or suppressing the affected symbols.

## 4. Preconditions — Domain Ownership

Before any export or schema change:

1. Every protected module in the affected surface MUST have an explicit domain classification.
2. Minimum classifications MUST include:
   - `NEUTRAL`
   - `FINANCIAL`
   - `MARKETPLACE_AUTHORITY`
   - `SHARED_APPROVED`
   - `UNKNOWN`
3. No module reachable from a protected surface may remain `UNKNOWN`.
4. Ownership MUST be based on architectural authority, not filename or directory naming alone.
5. Financial-coupled modules such as representation-finance paths and their dependent agreement paths MUST be classified consistently with their authority semantics.

**Failure:** Any unresolved classification → FAIL-CLOSED.

## 5. Preconditions — Target Public Surfaces

Before changing the combined barrel:

1. A dedicated Neutral public schema surface MUST be specified.
2. A dedicated Financial/Marketplace public schema surface MUST be specified.
3. The export contract for each surface MUST be explicit and enumerable.
4. No generic convenience barrel may recreate a prohibited combined surface.
5. The intended public entrypoint for each consumer class MUST be documented.
6. Every exported symbol MUST have a declared owner/classification.

The remediation target is domain separation, not simply deletion of selected exports from one barrel.

## 6. Preconditions — Shared Primitive Boundary

Any cross-domain dependency MUST be justified through an exact `SHARED_APPROVED` classification.

The shared allowlist MUST:

- identify exact module identities;
- state the reason each module is shared;
- define its permitted consumers;
- prove that the shared module does not transitively expose Financial/Marketplace authority;
- prove that it does not expose Neutral authorization implementation;
- reject broad directory, filename, namespace, or keyword-based approvals.

A proposed shared primitive without a complete transitive proof is not eligible.

## 7. Preconditions — Resolver Contract

The resolver model MUST be fixed before remediation begins.

The evidence package MUST explicitly cover the repository's actual resolution behavior, including:

- `package.json` exports;
- workspace package boundaries;
- TypeScript `moduleResolution`;
- configured custom conditions;
- relative and package imports;
- extension and index resolution;
- barrels and re-exports;
- declaration entrypoints where applicable;
- statically discoverable runtime loading.

A remediation that is safe under one resolver interpretation but unproven under the configured toolchain is not eligible.

## 8. Preconditions — Baseline Graph Evidence

Before modifying the barrel, the current branch-pinned graph MUST be captured sufficiently to establish:

```text
source → package entrypoint/export → barrel/re-export chain → target
```

for every known protected-domain crossing.

At minimum the evidence MUST preserve:

- tested commit SHA;
- source module identity;
- source classification;
- import/export form;
- package/export resolution;
- intermediate barrels;
- resolved target;
- target classification.

The known P3.1-J Neutral → `representationFinance` path MUST remain reproducible.

## 9. Preconditions — Forward Closure

Before remediation authorization, the affected Neutral surfaces MUST have a complete forward reachability baseline.

The baseline MUST answer:

> Which modules can a Neutral consumer resolve, directly or transitively, through every supported public resolution path?

Any unresolved reachable node is `UNKNOWN` and blocks remediation authorization.

## 10. Preconditions — Reverse Closure

The affected Financial/Marketplace surfaces MUST also have a reverse reachability baseline into Neutral authorization/core modules.

The evidence MUST establish whether any Financial or Marketplace entrypoint can acquire Neutral authorization implementation directly or transitively.

Repository-wide absence that cannot be proven is fail-closed.

## 11. Preconditions — Cycle Analysis

Strongly connected components MUST be evaluated before remediation.

No remediation may proceed while an unresolved protected-domain cycle remains.

The evidence MUST distinguish:

- harmless same-domain cycles;
- prohibited Neutral ↔ Financial cycles;
- prohibited Neutral ↔ Marketplace-authority cycles;
- cycles introduced through re-export barrels;
- package-level cycles affecting protected authority surfaces.

## 12. Preconditions — Runtime Escape Analysis

Before remediation, the relevant runtime-loading envelope MUST be defined and evaluated.

At minimum this includes statically discoverable:

- `import()`;
- `require()`;
- `createRequire()` targets;
- loader/bootstrap registries;
- package registration entrypoints;
- repository-controlled generated runtime artifacts.

A dynamically resolved protected-domain target that cannot be deterministically classified remains `UNKNOWN → FAIL-CLOSED` unless separately constrained by an explicit security allowlist or sandbox proof.

## 13. Preconditions — Declaration and Build Surfaces

The remediation plan MUST account for declaration/build resolution wherever it forms part of the package surface.

Evidence MUST cover, where applicable:

- `.d.ts` entrypoints;
- declaration re-exports;
- generated package metadata;
- build manifests;
- emitted package entrypoints.

Removing a source export while leaving an equivalent prohibited declaration/build surface is not remediation.

## 14. Preconditions — Consumer Inventory

Before changing exports, all affected consumers MUST be inventoried from the pinned graph.

The inventory MUST identify:

- Neutral consumers;
- Financial consumers;
- Marketplace-authority consumers;
- approved shared consumers;
- tests and fixtures;
- build tooling that resolves the affected package;
- runtime registration paths.

No consumer may be migrated based solely on a repository-wide textual search.

## 15. Preconditions — Remediation Invariants

Any future implementation MUST preserve these invariants:

```text
NEUTRAL → FINANCIAL                  = FORBIDDEN
NEUTRAL → MARKETPLACE_AUTHORITY      = FORBIDDEN
NEUTRAL → ESCROW/WALLET/SETTLEMENT   = FORBIDDEN
FINANCIAL → NEUTRAL AUTH IMPLEMENT.  = FORBIDDEN
MARKETPLACE → NEUTRAL AUTH IMPLEMENT.= FORBIDDEN
NEUTRAL ↔ FINANCIAL CYCLE            = FORBIDDEN
UNCLASSIFIED PROTECTED CROSSING      = FORBIDDEN
```

The remediation MUST NOT convert a prohibited dependency into an indirect dependency through a newly named barrel.

## 16. Preconditions — Regression Fixtures

Before remediation authorization, the future guard test contract MUST identify mandatory negative and positive fixtures.

Mandatory negative fixtures include:

1. Current P3.1-J shared-barrel leak.
2. Hidden Financial re-export.
3. Declaration-only Financial leak.
4. Reverse Financial → Neutral authorization dependency.
5. Prohibited domain cycle.
6. Statically resolvable dynamic Financial import.
7. Unknown protected runtime target.
8. Unauthorized shared primitive.
9. New export that expands Neutral closure without classification.

At least one positive fixture MUST demonstrate a compliant domain-separated export surface.

## 17. Preconditions — Non-Interference

Before any remediation write, there MUST be an explicit plan proving that the change does not:

- alter financial calculations;
- alter settlement/escrow/wallet behavior;
- alter marketplace authorization or execution;
- weaken authentication or authorization;
- mutate Production data;
- require a Production DB connection;
- silently change migration semantics;
- modify `main`.

If the proposed fix cannot demonstrate non-interference, remediation remains blocked.

## 18. Preconditions — Migration Separation

Schema/package separation MUST NOT be conflated with database migration.

A future export-surface remediation MAY be evaluated independently from database schema migration.

No migration may be introduced unless a separate migration-specific authorization is granted after its own evidence and rehearsal requirements are satisfied.

## 19. Preconditions — CI and Gate Isolation

Before implementation begins:

1. The future guard's CI execution model MUST be defined.
2. The guard MUST be deterministic for a pinned ref.
3. It MUST NOT depend on Production DB availability.
4. It MUST fail closed on resolver errors and incomplete protected graphs.
5. The known P3.1-J path MUST fail.
6. A compliant separated surface MUST pass.
7. CI activation itself requires a separately authorized implementation step.

Designing a CI contract does not authorize activating it.

## 20. Preconditions — Rollback

Before any remediation implementation, rollback MUST be defined as:

- isolated to the construction branch;
- reversible without touching `main`;
- reversible without Production DB writes;
- able to restore the prior export surface exactly;
- independently identifiable by commit SHA.

A remediation plan without a deterministic rollback point is not eligible.

## 21. Required Authorization Evidence Package

The future remediation request MUST contain one evidence package with:

```text
1. Pinned baseline commit
2. Domain classification manifest
3. Shared-approved allowlist
4. Resolver configuration/effective conditions
5. Forward graph closure
6. Reverse graph closure
7. Cycle analysis
8. Runtime escape analysis
9. Declaration/build analysis
10. Consumer inventory
11. Proposed target export surfaces
12. Non-interference analysis
13. Regression fixture contract
14. CI isolation plan
15. Rollback plan
```

Missing evidence for any mandatory item means remediation is not authorized.

## 22. Authorization Gate

The only acceptable transition is:

```text
BLOCKED
  ↓
All Preconditions Proven
  ↓
Independent Security Review
  ↓
Explicit Remediation Authorization
  ↓
Implementation on construction branch only
```

There is no implicit transition from documentation acceptance to code modification.

## 23. Prohibited Shortcuts

The following MUST NOT be accepted as remediation proof:

- deleting only the visibly referenced Financial export;
- renaming Financial modules;
- replacing one combined barrel with another combined barrel;
- relying on filename conventions;
- relying on grep alone;
- proving only direct imports;
- proving only TypeScript compilation;
- proving only runtime startup;
- proving only unit-test success;
- hiding prohibited exports behind declarations;
- relying on unused-code elimination;
- assuming dynamic loading is absent because no lexical import was found;
- treating unresolved paths as safe;
- using Production DB tests as a substitute for graph proof.
