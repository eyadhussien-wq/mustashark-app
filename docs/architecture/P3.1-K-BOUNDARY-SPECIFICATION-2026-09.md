# P3.1-K — Boundary Specification — 2026-09

**Status:** DEFINED / IMPLEMENTATION NOT AUTHORIZED  
**Branch:** `construction/lawyer-os-v1-p1-audit-2026-09`  
**Scope:** Specification only. No executable remediation is authorized by this artifact.

## 1. Purpose

This specification defines the target architectural boundary between the Neutral Authorization/Core surface and Financial/Marketplace schema surfaces following the conclusive P3.1-J finding:

```text
Neutral service
  → @workspace/db/schema
  → lib/db/src/schema/index.ts
  → Financial schema modules
```

The purpose is to prevent domain authority from crossing through a shared database-schema export surface while preserving a deliberate, reviewable path for genuinely shared primitives.

## 2. Security Invariant

The governing invariant is:

> Neutral authorization code MUST NOT be able to resolve, import, or transitively reach Financial/Marketplace schema modules through any public workspace package surface.

This is a module/export boundary requirement. A shared PostgreSQL database does not by itself authorize cross-domain schema access.

## 3. Target Domain Surfaces

### 3.1 Neutral surface

The Neutral surface contains only schemas and primitives required for Neutral identity/relationship/matter/document authorization and its audit trail.

Expected examples include:

- `neutralDocuments`
- `neutralMatters`
- `lawyerClients`
- explicitly approved shared identity primitives

The Neutral surface MUST NOT export or re-export Financial/Marketplace modules.

### 3.2 Financial/Marketplace surface

The Financial/Marketplace surface contains financial authority and execution schemas, including, as applicable:

- platform dues / commission state;
- representation finance / escrow / wallet state;
- payment proofs;
- lawyer proposals and quote/marketplace finance state where classified as financial authority.

These modules MUST NOT be reachable through the Neutral public schema surface.

### 3.3 Shared primitives

Shared primitives MUST be intentionally classified and explicitly allowlisted. Examples may include identity/user primitives when architecturally required.

A shared primitive is not permission to expose an entire domain barrel.

## 4. Export Contract

The future package contract SHALL make domain boundaries explicit.

Required properties:

1. Neutral consumers resolve only the Neutral-approved surface.
2. Financial consumers resolve only the Financial-approved surface.
3. A generic/shared barrel MUST NOT aggregate Neutral and Financial domain modules merely for convenience.
4. Domain barrels MUST NOT re-export another domain's authority modules.
5. Any intentionally shared module MUST have an explicit architectural classification and ownership.
6. Adding a new Financial/Marketplace schema MUST NOT automatically enlarge the Neutral import surface.
7. Public package exports MUST be intentionally enumerated rather than inferred from directory membership.
8. A package-level entrypoint reachable by Neutral code MUST itself satisfy the Neutral export contract; hiding a prohibited module behind another barrel remains prohibited.

## 5. Forbidden Edges

The following dependency edges are prohibited:

```text
Neutral → Financial schema
Neutral → Marketplace authority schema
Neutral → escrow/wallet/settlement/payout/commission schema
Neutral → Financial domain barrel
Financial → Neutral authorization implementation
Neutral ↔ Financial cycle
```

The prohibition applies to direct and transitive resolution.

A dependency that becomes reachable only after barrel expansion is still a prohibited edge.

## 6. Allowed Edges

The target architecture may allow:

```text
Neutral service → Neutral schema surface
Financial service → Financial schema surface
Neutral service → explicitly approved shared identity primitive
Financial service → explicitly approved shared identity primitive
```

Allowances MUST be explicit and minimal. The absence of a prohibition is not an allowlist entry.

## 7. Resolution Boundary

The boundary must be evaluated using the actual TypeScript/package resolution graph, not only textual import searches.

The future guard MUST account for:

- package `exports`;
- workspace package entry points;
- TypeScript `moduleResolution` and configured custom conditions;
- schema barrels;
- re-exports;
- direct imports;
- relative imports;
- package imports;
- transitive imports;
- compiler-resolved module identities.

The architectural test is therefore:

> Can a Neutral source file resolve a Financial/Marketplace schema module through any supported workspace import path?

If yes, the boundary fails closed.

## 8. Dependency Graph Requirements

The future graph guard SHALL establish, for the classified domain surfaces:

- Neutral → Financial = forbidden;
- Financial → Neutral = forbidden unless a separately approved shared primitive is involved;
- Neutral ↔ Financial cycle = forbidden;
- package-level Neutral/Financial cycles = forbidden;
- Neutral → approved shared primitives = allowed;
- Financial → approved shared primitives = allowed.

The guard must distinguish a permitted shared primitive from a domain-authority module.

## 9. Export-Surface Guard Requirements

The existing two-file Static Neutral Core guard is not sufficient for P3.1-J closure because it does not prove package/export reachability.

A future guard SHALL:

1. pin the tested commit/ref;
2. enumerate relevant domain schema modules;
3. resolve package entry points and `exports` conditions;
4. follow barrels and re-exports;
5. construct the branch-pinned dependency graph;
6. compute transitive closure;
7. fail on prohibited cross-domain reachability;
8. fail on unauthorized export expansion;
9. validate reverse dependencies and cycles;
10. validate shared crossings against an exact allowlist;
11. report the concrete source → package/export/barrel → target path.

A keyword scan may remain as a supplemental defense, but MUST NOT be treated as authoritative boundary proof.

No guard implementation is included in this specification.

## 10. Reverse Dependency and Cycle Requirements

Before boundary implementation is authorized, evidence MUST establish repository-wide, branch-pinned results for:

- Financial/Marketplace → Neutral reverse dependencies;
- Neutral ↔ Financial/Marketplace cycles;
- relevant package-level cycles;
- indirect re-export cycles;
- dynamically/runtime-resolvable loading paths where statically discoverable.

Where evidence is incomplete, the security status remains FAIL-CLOSED rather than assuming absence.

## 11. Runtime and Data Boundary

Module isolation is necessary but not sufficient.

Neutral authorization must remain unable to derive financial authority merely because database tables coexist or because an imported shared identity primitive exposes unrelated domain state.

Future validation should therefore distinguish:

1. schema/module reachability;
2. query/data selection;
3. service authority;
4. runtime execution/loading;
5. mutation authority.

P3.1-K specifically defines the schema/export/resolution boundary. It does not claim that all runtime/data-flow/non-interference properties have already been proven.

## 12. Public Surface Design Rule

The preferred architectural shape is explicit domain entrypoints, potentially including:

```text
@workspace/db/neutral
@workspace/db/financial
@workspace/db/shared
```

These names are illustrative, not an implementation decision in P3.1-K.

Whatever concrete design is later approved MUST preserve:

- Neutral cannot import Financial by package resolution;
- Financial cannot silently acquire Neutral authorization implementation;
- shared contains only explicitly approved primitives;
- adding Financial exports cannot alter Neutral exports implicitly;
- no convenience barrel recreates the prohibited combined surface.

## 13. Remediation Preconditions

No implementation may begin until the following are explicitly approved:

1. final domain classification;
2. exact public package surfaces;
3. exact shared-primitive allowlist;
4. import/export contract;
5. graph-guard algorithm and failure semantics;
6. treatment of generated declarations;
7. migration strategy for existing imports, if required;
8. CI enforcement point;
9. rollback/safety procedure.

The remediation must remain on the isolated construction branch and must preserve Production and `main` isolation.

## 14. CI / Security Gate Contract

The eventual CI gate SHALL enforce:

```text
Branch-pinned graph resolution
        ↓
Export-surface validation
        ↓
Transitive closure validation
        ↓
Reverse-edge validation
        ↓
Cycle validation
        ↓
Approved shared-primitive allowlist
        ↓
FAIL on any prohibited edge
```

The gate MUST be independent of Production DB connectivity and MUST use isolated/local test infrastructure where runtime tests are required.
