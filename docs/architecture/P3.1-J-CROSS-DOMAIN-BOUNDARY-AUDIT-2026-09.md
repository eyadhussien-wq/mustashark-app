## 7. Identity & Token Propagation

`requireAuth` accepts a Bearer token, verifies it, extracts `payload.userId`, then re-resolves the user from `usersTable`. It rejects missing/invalid identity and inactive/deleted users, and places the server-resolved user in `req.authUser`.

This is materially stronger than trusting a client-provided role or user object. Neutral document authorization independently re-checks the database user role and active/deleted state before authorization decisions.

Evidence: `requireAuth.ts` and `neutralDocumentAuthorization.ts`.

## 8. Authorization Authority Sources

The inspected Neutral authorization authority is server-side:

1. authenticated token establishes a user identifier;
2. server resolves the user from the database;
3. Neutral authorization checks role/account state and ownership/relationship/resource state;
4. denial is generated by server-side policy/service logic.

The policy receives an `actorRole`, but the inspected service layer does not use a client-supplied role as an authority source; it re-resolves the user before document authorization.

**Residual guard requirement:** future CI should explicitly reject request-body/query/header role fields being used as authorization authority.

## 9. Denial → Audit Trace

The denial path is explicitly implemented for Neutral document authorization:

`server identity/resource checks → denyDocumentAuthorization → recordNeutralAuthorizationDenied → recordNeutralAuditEvent`

The denial audit records actor, actor role, action `AUTHORIZATION_DENIED`, resource type/id, reason code, correlation id, and optional metadata. Audit persistence is transactionally appended to a hash-linked chain.

`neutralAudit.ts` defines chain/genesis hashes, previous-hash linkage, append-only insertion semantics, and verification. It also states that database migration blocks UPDATE/DELETE.

**Important finding:** this proves the Neutral service's denial-to-audit path at the inspected service layer. It does not by itself prove that every external route/controller denial in the whole API is impossible to emit without this path.

## 15. Recommended Static Guards

Design only — do not implement in P3.1-J Discovery.

1. Branch-pinned import graph for all Neutral Core files.
2. Explicit deny edges: Neutral → Financial and Neutral → Marketplace.
3. Reverse deny edges: Financial/Marketplace → Neutral authority modules where architectural direction forbids them.
4. Cycle detection with a dedicated failure class.
5. Resolution of TypeScript aliases, barrel exports, workspace package edges, and dynamic import candidates.
6. Role-authority guard: reject client-controlled role fields as authorization authority.
7. Data-boundary guard based on selected fields/imported schemas, not keyword matching alone.
8. Require denial paths to call the Neutral authorization audit surface.
9. Production DB target guard before and after security tests.
10. Emit machine-readable evidence of the graph and forbidden edges in CI.

## 18. Final Discovery Verdict

**P3.1-J Discovery Verdict: AMBER — structurally sound, repository-wide proof incomplete.**

The inspected Neutral Core surfaces demonstrate a coherent server-side authorization boundary and a strong denial-to-audit chain. No direct Financial/Marketplace dependency was found in the inspected executable Neutral surfaces.

However, the security claim required by P3.1-J is stronger than “the inspected files look clean.” A full GREEN verdict requires branch-pinned repository-wide dependency evidence covering aliases/barrels/dynamic edges, reverse dependencies, and circular dependencies, plus an explicit data-boundary inventory.

Therefore:

**DO NOT implement the Static Guard yet.**

Next approved sequence remains:

`Discovery → Evidence → Boundary Specification → Guard Design → Implementation → CI Proof`

The next gate is **Boundary Specification / Guard Design**, but only after the remaining branch-pinned graph evidence is obtained. No production or `main` action is authorized by this artifact.
