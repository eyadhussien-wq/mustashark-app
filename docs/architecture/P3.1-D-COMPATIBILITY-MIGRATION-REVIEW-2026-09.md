# P3.1-D Compatibility & Migration Review — 2026-09

Status: **APPROVED — SCHEMA DESIGN READY / IMPLEMENTATION STILL GATED**
Branch: `construction/lawyer-os-v1-p1-audit-2026-09`

## 1. Review scope

This review validates the approved Neutral Document schema design against the repository's existing Drizzle/PostgreSQL conventions and the already-constructed Neutral Core ownership/matter boundaries.

No database connection was used and no database mutation was performed in this review.

## 2. Existing schema compatibility

The repository uses Drizzle PostgreSQL schema exports through `lib/db/src/schema/index.ts`; the Drizzle configuration points at that index as the schema authority.

The Neutral Lawyer↔Client relationship uses a dedicated `lawyer_clients` root with a unique `(lawyer_id, client_id)` pair and lifecycle state `active | archived`.

The Neutral Matter root uses `neutral_matters`, with `lawyer_id`, `client_id`, title, lifecycle state `active | completed | archived`, and no agreement/payment dependency.

The new Neutral Document root should follow the same convention: text primary key, explicit user FKs, PostgreSQL enum lifecycle, timestamps, indexes for ownership/scope, and no legacy-domain FK.

## 3. Approved Neutral Document persistence model

### `neutral_documents`

Required fields:

- `id` — text primary key
- `lawyer_id` — required FK to `users.id`
- `matter_id` — nullable FK to `neutral_matters.id`
- `title` — required
- `storage_key` — required storage reference; not an authorization credential
- `content_hash` — nullable integrity metadata
- `status` — `draft | active | archived`
- `created_at`
- `updated_at`
- `archived_at` nullable

Indexes:

- lawyer_id
- matter_id
- status

### `neutral_document_shares`

Required fields:

- `id` — text primary key
- `document_id` — required FK to `neutral_documents.id` with cascade delete only as a technical orphan-prevention measure
- `client_id` — required FK to `users.id`
- `status` — `active | revoked`
- `created_at`
- `updated_at`
- `revoked_at` nullable

Constraint:

- unique `(document_id, client_id)`

Indexes:

- document_id
- client_id
- status

## 4. FK and deletion semantics

`lawyer_id` and `client_id` references must use the same identity authority as existing Neutral Core tables.

A Neutral Document must not have an FK to:

- agreements
- legal representation documents
- quotes/proposals
- payment proofs
- platform dues
- representation finance
- wallet/bank settlement
- bookings
- legacy cases
- document handovers
- marketplace entities

Deleting a user is an existing identity/data-lifecycle policy and is not redefined by this document.

The schema must not introduce a new cascade path that can erase unrelated Neutral Core resources merely because a share is revoked.

Revocation is a state transition, not deletion.

## 5. Matter compatibility

`matter_id` is nullable so a lawyer-owned document may exist independently of a Matter.

When `matter_id` is present, service-layer authorization must prove that the Matter belongs to the same `lawyer_id` before insertion or access.

The database FK guarantees referential existence only; it does not replace application authorization.

## 6. Explicit sharing compatibility

Sharing is a separate relation because ownership and access are different authorities:

`lawyer ownership → document`

`client access → active share`

A client must never gain access merely because `client_id` appears in a request, because the document ID is known, or because the client has another relationship with the lawyer.

A share may be revoked without deleting the document or its historical metadata.

## 7. Migration decision

**READY TO IMPLEMENT, but not yet executed.**

The compatibility review found no structural reason to reject the approved two-table Neutral Document design.

The next implementation step may create:

1. a dedicated Drizzle schema file for the Neutral Document tables;
2. one migration creating the required enums/tables/FKs/indexes;
3. explicit exports from `schema/index.ts`.

The migration must be additive and must not alter or backfill legacy document tables.

## 8. Storage remains separately gated

Creating database metadata is not permission to upload files or expose storage endpoints.

Storage implementation requires a separate review covering:

- private bucket/object policy
- opaque storage keys
- server-side ownership authorization before reads/writes
- content-type/size validation
- upload/download authorization
- no direct client-controlled storage path
- integrity verification
- audit events for sensitive operations

## 9. Security invariants

- `ID != AUTHORIZATION`
- `storage_key != AUTHORIZATION`
- `ROLE != AUTHORIZATION`
- `NO ACTIVE SHARE = NO CLIENT DOCUMENT ACCESS`
- `NO OWNERSHIP = NO LAWYER DOCUMENT ACCESS`
- `REVOKE SHARE != DELETE DOCUMENT`
- `matter_id` does not widen lawyer scope
- admin role does not automatically grant confidential document access
- no Neutral Document operation may require financial, marketplace, custody, escrow, payout, settlement, or commission state.
