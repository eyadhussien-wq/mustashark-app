# Mustashark — P3.1-D Neutral Document Implementation Review

**Effective:** 2026-09-01  
**Construction branch:** `construction/lawyer-os-v1-p1-audit-2026-09`  
**Status:** `DECISION RECORDED / IMPLEMENTATION NOT YET AUTHORIZED`

## 1. Review objective

Determine from the current repository evidence whether Neutral Lawyer OS documents can safely reuse the existing `documents` persistence surface or require a separate Neutral Document root.

No `main` or Production mutation is permitted by this review.

## 2. Evidence reviewed

### Existing `documents`

The current `documents` table contains useful operational fields such as `ownerId`, `title`, `fileName`, `mimeType`, `storageKey`, status, and timestamps. However, it also requires `caseId` and therefore inherits the current case domain boundary.

The current document-handover controller also requires `caseId`, verifies the document against that case, requires active case membership for the recipient, and drives a physical/logistical handover state machine. This is not a neutral document ownership model.

### Existing legal-representation documents

`legal_representation_documents` is explicitly tied to `agreementId` and optionally `caseId`, with representation-specific document type/status/review fields. It remains legacy representation infrastructure and is not a Neutral Core persistence root.

### Existing Neutral contracts

`NeutralDocument` already defines the intended neutral shape: document identity, lawyer ownership, optional Matter scope, title, storage reference, and content integrity hash. The contract intentionally carries no financial, marketplace, settlement, wallet, escrow, or client-fund authority.

## 3. Decision

**Do not extend the existing `documents` table for the Neutral Core at this stage.**

The evidence shows that the existing table is a legacy case-rooted surface and is consumed by a case/handover workflow whose authorization semantics are materially different from the approved Neutral Document model.

A separate Neutral Document persistence root is the safer construction choice because it:

1. prevents legacy case/handover assumptions from becoming Neutral Core invariants;
2. keeps legal-representation documents isolated;
3. allows Matter scope to be optional;
4. permits explicit document sharing to be designed independently;
5. avoids a risky compatibility migration on an existing legacy table;
6. preserves legacy data and behavior without destructive conversion.

## 4. Proposed minimum Neutral persistence boundary

The implementation should introduce a dedicated Neutral Document table only after the schema design is reviewed and approved. Minimum authoritative fields should cover:

- `id`
- `lawyerId`
- optional `matterId`
- `title`
- document classification/type
- `storageKey`
- optional `contentHash`
- lifecycle status (`draft`, `active`, `archived`)
- created/updated timestamps
- optional archive timestamp

Explicit sharing should be represented by an authorization relation rather than inferred from the document ID or legacy case membership. Version history, audit records, and export state should remain separately governed concerns unless the existing architecture proves a safe reuse path.

## 5. Authorization construction rule

The Neutral Document service must authorize using the authenticated server-side actor plus ownership/scope checks.

Minimum rules:

- lawyer → own document only;
- matter-scoped document → Matter must belong to the same lawyer;
- client → only explicitly shared document scope;
- archived/revoked relationship → no new access under relationship policy;
- admin role alone → no confidential document access;
- resource IDs are never authorization;
- authorization failure must avoid unnecessary existence disclosure.

## 6. Storage boundary

The application should store a storage reference, not treat a public URL as authorization. Provider credentials and object-level storage policy remain outside the Neutral Document domain contract.

## 7. Legacy isolation

Do not delete or rewrite:

- `documents`;
- `document_handovers`;
- `legal_representation_documents`;
- legacy case/document services and behavioral tests.

They remain historical/regulated/legacy surfaces until a separately approved migration or retirement plan exists.

## 8. Migration gate

**No migration is created by this review.**

Before migration, the next implementation step is schema design for the dedicated Neutral Document root and its explicit sharing relation, followed by a compatibility/dependency check and CI/typecheck plan.
