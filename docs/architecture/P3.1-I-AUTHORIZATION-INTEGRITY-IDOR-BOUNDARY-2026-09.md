# P3.1-I — Authorization Integrity, Cross-Context Access Control & IDOR Defense

**Status:** IN PROGRESS — implementation evidence required
**Construction branch:** `construction/lawyer-os-v1-p1-audit-2026-09`
**Security Hold:** ACTIVE

## Security boundary

P3.1-I is a Neutral Core authorization gate. It is independent of financial, marketplace, commission, escrow, wallet, settlement, payout, platform-dues, payment-collection, and client-fund authorities.

## Authorization invariant

A Neutral Core access decision is valid only when all applicable boundaries are satisfied:

`Authenticated active actor ∧ correct role ∧ active relationship ∧ valid matter lifecycle ∧ resource in actor scope ∧ resource matches matter scope ∧ operation permitted`

Any missing term fails closed.

## Existence disclosure policy

HTTP `403` versus `404` is not hard-coded globally. The policy decides whether protected-resource existence may be confirmed:

- `hide` → `404` for enumeration-sensitive scope failures.
- `confirm` → `403` when the actor is already entitled to know the protected context exists but the operation is denied.

This prevents `403` from becoming an unintended existence oracle.

## Cross-context checks

The implementation must revalidate server-side state at authorization time for:

- inactive/deleted actors, including stale JWTs;
- archived/inactive Lawyer ↔ Client relationships;
- archived Matters;
- resources that no longer belong to the authenticated actor's scope;
- resources whose Matter scope does not match the authenticated client/lawyer context;
- admin attempts to bypass Neutral confidential-data boundaries.

A transferred client does not create cross-lawyer authority. Relationship ownership remains explicit per lawyer-client pair.

## IDOR / tampering rule

Client-supplied identifiers are lookup selectors, never authority. Every sensitive read/write must resolve ownership and context on the server.

## Denial audit rule

Authorization denials must append an immutable P3.1-H audit event:

- `action = AUTHORIZATION_DENIED`
- `outcome = denied`
- actor identity and role
- resource type and requested resource identifier
- explicit reason code
- correlation ID when available
- minimal metadata only

No password, JWT, session secret, document contents, storage credential, or unnecessary legal/financial data may be written to the audit event.

Audit failure is fail-closed for the denial path: the service must not silently report a normal authorization denial when its required security audit entry could not be persisted.

## Error-boundary rule

Expected ownership/relationship denials may be translated into authorization decisions. Database/infrastructure failures must not be caught and misclassified as authorization denials.

## Evidence required for closure

P3.1-I cannot close until CI proves both positive and negative cases, including:

1. authorized same-scope access succeeds;
2. cross-lawyer IDOR is denied;
3. cross-matter tampering is denied;
4. inactive/deleted actor is denied;
5. archived relationship is denied;
6. archived Matter is denied;
7. admin confidential bypass is denied;
8. existence disclosure policy is deterministic;
9. authorization denials are audit-recorded with explicit reason codes/correlation IDs;
10. no blocked-domain dependency is introduced;
11. Production DB Guard remains green before and after the gate.

The gate remains open until the CI evidence is green for both allowed and denied paths.
