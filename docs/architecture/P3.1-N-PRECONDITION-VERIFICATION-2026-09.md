## Extension A — Virtual Split Contract

### A.1 Objective

Define the future public export contract theoretically, without prescribing or performing the implementation. The contract must make Neutral and Financial/Marketplace schema authority separately enumerable and independently resolvable.

The target conceptual topology is:

```text
@workspace/db
        │
        ├── Neutral public surface
        │      └── Neutral schema authority only
        │
        ├── Financial public surface
        │      └── Financial schema authority only
        │
        └── Shared-approved surface
               └── exact approved primitives only
```

### A.2 Required contract properties

1. A Neutral consumer MUST have a dedicated public resolution path whose reachable schema surface contains only Neutral-owned modules plus explicitly approved shared primitives.
2. A Financial/Marketplace consumer MUST have a dedicated public resolution path for its own authority surface.
3. A shared primitive surface MUST contain only explicitly classified `SHARED_APPROVED` identities.
4. No public convenience barrel may combine Neutral authorization/data authority with Financial/Marketplace authority.
5. The root package entrypoint MUST NOT reintroduce a combined domain barrel through `export *`, direct re-export, declaration re-export, generated metadata, or an equivalent package surface.
6. Removing a visible Financial export from a barrel is insufficient unless resolver-aware transitive closure proves the complete Neutral surface remains free of Financial/Marketplace authority.
7. The future contract must be testable against package `exports`, workspace boundaries, TypeScript `bundler` resolution, custom `workspace` conditions, extension/index resolution, barrels, re-exports, declarations, and statically discoverable runtime loading.

### A.3 Non-negotiable reachability invariants

```text
NEUTRAL → FINANCIAL                  = FORBIDDEN
NEUTRAL → MARKETPLACE_AUTHORITY      = FORBIDDEN
NEUTRAL → ESCROW/WALLET/SETTLEMENT   = FORBIDDEN
```

## Extension B — Runtime / Build Escape Policy

### B.1 Objective

Convert the discovered runtime/build escape capability into a precise future guard requirement without treating the existence of a loader primitive as a violation by itself.

### B.2 Loader rule

The future resolver-aware guard MUST inspect statically discoverable runtime loading mechanisms, including but not limited to:

- `createRequire`;
- `require`;
- `globalThis.require`;
- dynamic `import()`;
- loader/bootstrap registries;
- package registration mechanisms;
- generated/emitted runtime entrypoints;
- equivalent statically discoverable mechanisms capable of resolving protected modules.

### B.3 Violation semantics

`createRequire` or another loader primitive is **not**, by itself, a security violation. The violation occurs when the loader can be resolved to a protected target outside the approved resolution contract.

The future guard MUST classify the result as:

```text
PROVEN ALLOWED TARGET       → PASS
PROVEN FORBIDDEN TARGET     → VIOLATION
UNRESOLVED / INCOMPLETE     → UNKNOWN → FAIL-CLOSED
```

Therefore:

> Any statically discoverable runtime loading path capable of reaching a Financial/Marketplace authority module from a Neutral context, when not proven within the Allowed Import/Resolution Contract, MUST be treated as a security violation or unresolved fail-closed condition according to the evidence available.

### B.4 Build/declaration escape parity

The same rule applies to generated artifacts and declaration/build surfaces. A path MUST NOT be considered safe merely because the source-level import graph appears clean.

The future proof must account for:

```text
source
  → package export
  → barrel / re-export
  → declaration / generated metadata
  → emitted build entrypoint
  → statically discoverable runtime loader
  → resolved protected target
```

Any unresolved protected target remains `UNKNOWN` and therefore blocks remediation eligibility.
