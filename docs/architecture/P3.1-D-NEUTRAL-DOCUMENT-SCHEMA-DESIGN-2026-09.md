# P3.1-D — Neutral Document Schema Design

**Status:** APPROVED DESIGN / IMPLEMENTATION NOT YET AUTHORIZED
**Branch:** `construction/lawyer-os-v1-p1-audit-2026-09`
**Date:** 2026-09

## 1. Purpose

Define the smallest persistence model required for Neutral Core documents and explicit sharing before any storage implementation or migration.

This document is design authority only. It does not authorize storage-provider integration, data migration, legacy-table alteration, or production mutation.

## 2. Design Decision

Use a separate Neutral Document root rather than extending the legacy `documents` table.

The existing `documents` table requires `caseId`, while Neutral Core documents must be able to exist independently of legacy case, agreement, payment, representation, or handover state. The current handover model also directly depends on `documents` and `caseId`.

The legacy `legal_representation_documents` table remains isolated because it is agreement/case-oriented and belongs to the regulated/legacy representation flow.

## 3. Minimum Tables

### 3.1 `neutral_documents`

Required columns:

- `id` — opaque text primary key.
- `lawyer_id` — FK to `users.id`; owner authority.
- `matter_id` — nullable FK to Neutral Matter; document may exist at lawyer-workspace level before being attached to a matter.
- `title` — required human-readable title.
- `storage_key` — required opaque storage reference; this is not a public URL.
- `content_hash` — nullable integrity hash until content is actually stored/hashed.
- `status` — `draft | active | archived`.
- `created_at` / `updated_at` — server timestamps.
- `archived_at` — nullable server timestamp.

Indexes:

- `(lawyer_id)`
- `(matter_id)`
- `(lawyer_id, status)`

No columns for agreement, quote, payment, wallet, settlement, escrow, client funds, commission, marketplace, or legal-representation state.

### 3.2 `neutral_document_shares`

Explicit sharing is represented separately from ownership.

Required columns:

- `id` — opaque primary key.
- `document_id` — FK to `neutral_documents.id`.
- `client_id` — FK to `users.id`.
- `status` — `active | revoked`.
- `created_at` / `updated_at` — server timestamps.
- `revoked_at` — nullable server timestamp.

Constraints/indexes:

- unique `(document_id, client_id)`
- index `(client_id, status)`
- index `(document_id, status)`

The table records authorization scope; it does not transfer ownership.

## 4. Why No Generic ACL Yet

Do not introduce a generic `principal_type/principal_id` ACL in P3.1-D.

The current Neutral Core has one explicit client-sharing requirement and one owner role. A generic ACL would enlarge the authorization surface without evidence that firms, assistants, teams, or other principals need document-level sharing now.

Future multi-user firm/assistant permissions can extend the model through a separately approved authorization design.

## 5. Sharing Semantics

- Lawyer owns the document.
- Client access exists only through an active share row.
- Creating a share does not change `lawyer_id`.
- Revoking a share stops client access without deleting the document.
- Deleting a relationship must not implicitly delete the document.
- A client cannot grant themselves access by supplying `documentId` or `clientId`.
- `clientId` in a request is never trusted as actor identity; authenticated identity comes from server-side auth context.
- A lawyer may share only a document they own and, when `matter_id` is present, only within a matter they are authorized to access.
- A client may read only documents for which an active share exists and the client account remains eligible under the authorization policy.

## 6. Matter Integrity

When `matter_id` is non-null, the implementation must verify that the matter belongs to the same `lawyer_id` as the document.

This must be enforced server-side; the database FK alone is insufficient because a document could otherwise reference a matter owned by another lawyer.

## 7. Status Semantics

`draft → active → archived`

- `draft`: document record exists but is not necessarily client-visible.
- `active`: eligible for authorized access according to ownership/share policy.
- `archived`: retained record; no destructive deletion implied.

Archive is not a substitute for access control. A read path must check status and scope explicitly.

## 8. Storage Boundary

`storage_key` is an opaque reference only.

P3.1-D does not select or integrate a storage provider. Storage authorization, signed URLs, upload/download policy, malware scanning, retention, and content encryption require a later implementation/security review.

The application must never treat `storage_key` as a client authorization token.

## 9. Integrity Boundary

`content_hash` is metadata for integrity verification.

Hashing must be performed server-side from the stored content or trusted upload stream. Clients must not be allowed to assert arbitrary integrity hashes as authoritative evidence.

## 10. Audit Boundary

Sensitive operations must map to the existing Neutral audit contract:

- `create`
- `read`
- `update`
- `archive`
- `share`
- `export`

Audit records must identify the authenticated actor server-side and the affected document/share resource.

## 11. Legacy Isolation

The following remain outside Neutral Document authority:

- `documents`
- `document_handovers`
- `legal_representation_documents`
- agreements
- representation finance
- payment proofs
- platform dues/commission
- wallets/bank settlement
- escrow/client funds
- marketplace ranking/referral monetization

Existing legacy implementations remain intact and are not migrated into the Neutral model by this design.

## 12. Implementation Gate

Before implementation:

1. Confirm schema naming does not collide with existing enums/tables.
2. Confirm Neutral Matter FK target and deletion semantics.
3. Add schema exports only after the new schema is created.
4. Create migration only after the schema is reviewed against current DB/migration history.
5. Implement service-level ownership and share authorization before controllers.
6. Add IDOR tests for owner/client/cross-tenant access.
7. Do not connect a storage provider yet.

## 13. Explicit Non-Goals

This design does not authorize:

- document upload/download endpoints,
- storage-provider credentials,
- signed URL generation,
- migration of existing legacy documents,
- document handover reuse,
- client-side ACL decisions,
- subscription entitlement enforcement,
- marketplace features,
- financial features.

## 14. Exit Criteria for P3.1-D Schema Design

P3.1-D Schema Design is complete when the model is approved as the minimum Neutral persistence boundary and the implementation gate remains closed until compatibility and migration review pass.
