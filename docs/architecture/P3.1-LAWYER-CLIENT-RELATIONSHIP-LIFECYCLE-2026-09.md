# Mustashark — Lawyer–Client Relationship Lifecycle

**Effective:** 2026-09-01  
**Construction branch:** `construction/lawyer-os-v1-p1-audit-2026-09`  
**Status:** `APPROVED / P3.1-B LIFECYCLE BASELINE`

## 1. Purpose

Define the simplest secure lifecycle for connecting a lawyer and client without making an invitation, request, account creation, or professional verification equivalent to authorization.

## 2. Two relationship entry paths

### Path A — Lawyer invites client

```text
Lawyer
  → Invite Client
  → Secure Invitation
  → Client authenticates or creates Client account
  → Client explicitly accepts
  → Active Relationship
```

Opening the invitation does not grant access. Account creation does not grant access. Acceptance activates the relationship only after server-side validation.

### Path B — Client requests an existing lawyer

```text
Client
  → Find existing lawyer
  → Request Lawyer
  → Lawyer authenticates and explicitly accepts
  → Active Relationship
```

The client request expires after **7 days** if not accepted. Expiry changes the request to `expired`; the historical request is retained for auditability and is not silently deleted.

## 3. Invitation/request is not a relationship

The system MUST keep the security credential/request lifecycle separate from the durable Lawyer–Client relationship.

```text
Invitation / Request ≠ Active Relationship
```

The existing `lawyer_clients` table remains the durable relationship authority with `active | archived` state. Invitation/request records should be modeled separately when implementation begins so one relationship can have multiple historical invitation/request attempts.

## 4. Minimum security requirements

- Invitation tokens are opaque, high-entropy, one-time credentials.
- Tokens expire and can be revoked.
- Raw tokens should not be stored when a secure hash is sufficient.
- Tokens must not contain sensitive profile data or act as authorization by themselves.
- Acceptance requires an authenticated account of the intended role.
- Where an invitation is bound to verified contact information, the server validates the verified contact; request-body values are not trusted as proof.
- After acceptance, the invitation/request cannot be reused to obtain access.
- Resource IDs never establish authorization.
- Server-side authenticated identity is authoritative.

## 5. Role separation

A client cannot create a lawyer identity through the relationship flow.

A person who wants to become a lawyer follows a separate:

```text
Lawyer Application → Professional Verification → Approval
```

This process is outside Lawyer–Client relationship linking.

## 6. Client account creation

If the receiving party has no account:

```text
Secure Invitation / Request
  → Create account for the correct role
  → Required identity/contact verification
  → Authenticate
  → Review the relationship target
  → Explicit acceptance (where that party is the receiver)
```

Creating the account MUST NOT automatically accept the relationship.

The first-run client experience should be minimal. Internal concepts such as tenant, authorization scope, and relationship state are not exposed unnecessarily in the UI.

## 7. Unlink / end relationship

Unlinking must not delete the identity or historical records.

Normal end of working relationship:

```text
active → archived
```

Security/exception termination may use:

```text
active → revoked
```

The exact persistence state for `revoked` is a later implementation decision; the security requirement is immediate authorization re-evaluation and an audit event.

A new active relationship is required before new relationship-scoped access is granted.

## 8. Historical data

Archiving/revoking a relationship does not delete historical records. Access to retained historical data is policy-controlled and must never be inferred merely from possession of an old relationship or resource ID.

## 9. Audit events

The implementation should be able to record at minimum:

- `INVITATION_CREATED`
- `INVITATION_VIEWED`
- `INVITATION_ACCEPTED`
- `INVITATION_REJECTED`
- `REQUEST_CREATED`
- `REQUEST_ACCEPTED`
- `REQUEST_REJECTED`
- `REQUEST_EXPIRED`
- `RELATIONSHIP_ACTIVATED`
- `RELATIONSHIP_ARCHIVED`
- `RELATIONSHIP_REVOKED`
- `RELATIONSHIP_REACTIVATED`

Each event should use server-generated actor identity and timestamp and avoid storing unnecessary sensitive data.

## 10. Authorization invariant

```text
Authenticated Identity
        +
Explicit Consent by the receiving party
        +
Active Relationship
        ↓
Authorized relationship scope
```

This does not replace resource-level authorization. Matters, documents, messages, schedules, and exports must still enforce their own server-side scope rules.

## 11. Social login boundary

The client onboarding path may support:

- Google
- Apple
- Microsoft

Facebook is deferred from V1.

Social authentication proves authentication with the provider; it does not by itself prove Lawyer–Client relationship authorization or professional lawyer verification.

## 12. Non-goals / hard blocks

This lifecycle does not authorize:

- marketplace ranking or referral monetization
- commission
- payment collection
- wallet or settlement
- escrow
- client-fund custody
- automatic lawyer professional approval
- automatic role conversion from client to lawyer

## 13. Implementation rule

No migration is authorized by this document alone.

When implementation begins, first inspect the current invitation/auth/identity surfaces and then choose the minimum schema/API change required by evidence. Preserve legacy records and avoid destructive cleanup.
